# zopen constraints for pip on z/OS -- SOURCE FILE, NOT FOR DIRECT USE
#
# Pointing PIP_CONSTRAINT at this file does not work: the version pins are
# generated and live only in the published copy, so this half on its own lets
# pip pick a newer release of a package we build and resolve it to an sdist.
#
# This is the hand-maintained half. The published file that users point pip at
# is generated from this plus the current contents of the wheel index, so the
# version pins below are never written here by hand:
#
#   https://repo.zopen.community/pulp/content/constraints/zopen-constraints.txt
#
# Use it with the zopen wheel index:
#
#   export PIP_EXTRA_INDEX_URL="https://repo.zopen.community/pypi/wheels/simple/"
#   export PIP_CONSTRAINT="https://repo.zopen.community/pulp/content/constraints/zopen-constraints.txt"
#   pip install <package>
#
# A pip constraints file says "if this package gets installed, it must satisfy
# this specifier". It installs nothing and modifies no package's metadata,
# which is the honest place to record a platform limitation: Requires-Dist
# describes what a package needs, not what a platform can support.
#
# Two kinds of entry:
#
#   1. Packages zopen builds for z/OS. PyPI has no z/OS wheel for these, so a
#      newer upstream release resolves to an sdist that cannot be compiled
#      here. Pinning to the published version leaves the zopen wheel as the
#      only candidate -- pip prefers a compatible wheel over an sdist at the
#      same version, so --only-binary is not needed.
#
#      GENERATED. Do not add these by hand; the publish job derives them from
#      the wheel index so they cannot go stale.
#
#   2. Upstream packages that grew a native dependency, capped below the
#      release that introduced something unbuildable.
#
#      MANUAL, and listed below. Nothing can infer these: they are properties
#      of a third-party package's dependency tree, discovered when an install
#      starts compiling from source.
#
# If the server also runs a PyPI pull-through, its remote carries an "excludes"
# list encoding the same policy -- but in the inverse language, so the two
# cannot be generated from each other and must be kept in step by hand:
#
#   intent                        this file            Pulp exclude
#   ---------------------------   ------------------   ----------------
#   keep pip below foo 2.0        foo<2.0              foo>=2.0
#   never shadow our wheel        pydantic-core==X     pydantic-core
#
# A Pulp exclude says "do not serve versions matching this"; a constraint says
# "pip must choose something matching this". Writing "pydantic-core==X" as an
# exclude would hide our own wheel and keep serving PyPI's newer ones.
#
# Which of the two applies depends on how a user configured pip, so a
# disagreement between them shows up as behaviour that differs per user.
#
# Removing a cap therefore means editing both sides. The publish job only ever
# adds to the excludes list, so a bound it no longer needs stays there until
# someone deletes it, and the proxy keeps enforcing a ceiling that this file
# has already dropped.

# --- capped to avoid unported native dependencies ----------------------------

# mcp was capped at <1.20.0 because 1.20.0 added pyjwt[crypto], which pulls in
# cryptography. cryptography is now published for z/OS, so the cap is gone --
# verified on 3.12 that mcp 2.0.0 resolves through it and works.
#
# That note used to add: on 3.13 and 3.14 mcp still failed, because
# pydantic-core and rpds-py were published cp312-only and pip fell through to
# their sdists. Both are now built for 3.12, 3.13 and 3.14, so that no longer
# applies either.

# fastmcp was capped at 2.0.0 because 3.x requires watchfiles, which is Rust.
# watchfiles is now published for 3.12, 3.13 and 3.14, so the reason is gone and
# the cap with it.
#
# It was inert in practice -- the publish job drops a cap on any package it also
# pins from the index, and fastmcp is one -- but it was wrong, and it would have
# started biting the moment fastmcp left the index. The rationale being stale is
# the real problem: this file is where someone looks to find out why a version
# is held back.
#
# No matching change on the Pulp side. Its "fastmcp" exclude is the bare-name
# kind that stops the proxy shadowing our own wheel, which the publish job
# maintains, not a ceiling paired with this cap.
